# Chiller — ночной аудит 18 октября 2026

## Вывод

Chiller уже пригоден для ежедневных небольших задач с проверкой diff и запуском тестов. Реальный DeepSeek успешно выполнил все 14 задач полного корпуса и 5 задач компактного профиля, включая точные изменения, сохранение пользовательских правок и многофайловую логику. Это хороший рабочий preview, но не основание обещать автономную безошибочную работу на произвольном проекте.

Главные следующие шаги — надёжность новых функций и интеграция уже существующих улучшений вставки, а не увеличение числа инструментов. На master картинки пока не передаются модели как пиксели; соответствующая реализация лежит в отдельном worktree. Компактный профиль исключает инструменты чтения вложений и показа результатов. Эти ограничения особенно важны для исходной цели — небольших моделей.

## Бюджет и расход

Единый proxy резервировал стоимость **до каждого HTTP-запроса**, включая помощников и повторы. Верхняя оценка входа: `2 × UTF-8 bytes JSON + 4096` токенов; весь вход оценивался по пиковой цене cache-miss $0.30/M, максимальный выход — $1.20/M. Возврата резерва не было даже после успеха. Guard: $2.25, дополнительный запас $0.25 до разрешённых $2.50, максимум 150 запросов. Запросы изображений этим guard не разрешались.

Итого **112 запросов / 112 завершённых ответов**, резерв **$1.357653**. Provider usage: 391 656 входных токенов (337 792 cached, 53 864 miss), 11 714 выходных. Оценка по опубликованным weekend/off-peak ставкам: **$0.016121376**; это расчёт по usage, **не измеренное списание с баланса**. Пиковая оценка с учётом сообщённого кеша вдвое выше. Proxy остановлен после сценариев; остаток бюджета не тратился ради количества тестов.

Цены проверены 18 октября по [официальной странице DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/). Она называет текущий Flash `DeepSeek-V4.1-Flash-1017` и заявляет vision. ## Вставка и интерфейс

Измерен именно метод master `encodeClipboardImage` на Swing EDT, три вызова на синтетическое изображение 3840×2160:

| Изображение | Время каждого вызова | Результат |
|---|---|---|
| Однотонное 4K | 198.1 / 117.5 / 113.6 мс | PNG 24 256 байт |
| Шум 4K | 616.9 / 662.0 / 705.0 мс | отклонён после кодирования (>4 MiB) |

Это воспроизводимая блокировка UI-потока на сотни миллисекунд; обещать «почти мгновенно» для master нельзя. Три прогона не являются p95. Измерение не включает получение системного clipboard, запись, декодирование preview и first-paint. Одно UTF-8 преобразование текста 5 KiB / 1 MiB / 8 MiB заняло 0.59 / 0.22 / 1.70 мс; малые числа зависят от прогрева, это не end-to-end время вставки.

На master `encodeClipboardImage` запускается из UI-coroutine без переключения dispatcher. В отдельной ветке уже есть pending-chip, фоновая подготовка, сокращение лишних UTF-8 преобразований и реальная image_url-сериализация. Это существенный прогресс, но он ещё не в проверенном master.

Риски ветки по коду: изображение декодируется/масштабируется/JPEG/base64-кодируется заново на каждом раунде; нет кеша подготовленного payload. Для не-BufferedImage сначала создаётся полноразмерный буфер. Несколько вставок не имеют явного ограничения конкуренции. Получение native clipboard snapshot всё ещё может задержать UI до pending-chip. Project map имеет лимиты сканирования, но конечный prefix может превысить заявленный maxChars. Эти выводы — review, не измерения ветки.

Повторно отрисованы синтетические таблицы/изображения и RunPanel в light/dark, ширины 1120/560. Просмотрены light-wide и dark-narrow: таблица имеет ровные колонки и перенос заголовков, график читаемый, без обрезки, есть кнопка раскрытия, результат остаётся видимым при свёрнутых actions. Это подтверждает прогресс относительно старого скриншота. Полное окно, dropdown, жесты zoom и системная вставка не приняты нативно в этом аудите.

По дизайну следующими проверять плотность статистики Studio (основные показатели сверху, подробности по раскрытию), ширину таблиц с длинными ячейками, доступность и фокус клавиатуры у viewer, и pending/error-состояния composer. Не делать ещё один визуальный редизайн до проверки реальных сценариев.

## Найденные слабые места и порядок работ

### P1 — привязка auto-verify к исходному диалогу

Долгая проверка завершается после переключения проекта; старый результат мог обновить новое окно и отправить repair-prompt в текущий проект. Исправлено локально: результат и follow-up проверяют исходную session/settings/process-service/epoch под общим mutex, а enqueue repair атомарен с этой проверкой. После переключения старый результат отбрасывается. Снимок завершённого run берётся из соответствующего AgentCoordinator, а не потенциально отстающего UI collector. Добавлены проверка контекста и controller-регрессия: принять успешный результат, сменить workspace, доставить запоздалый failed-result — новый чат остаётся без repair-сообщения. Отдельно targeted AutoVerifyTest прошёл. Это тест завершения callback с fake process service, не интерактивный race через окно..

### P1 — минимальный профиль должен сохранять базовые возможности

`ModelProfiles.CORE_TOOLS` не включает `read_artifact` и `show_file`. Вставленный большой текст превращается в artifact, но компактный агент лишён штатного чтения; созданный график не может нормально предъявить. Добавить обязательный набор возможностей независимо от размера профиля либо подмешивать tools по наличию вложений/ожидаемому результату.

Приёмка: одинаковые сценарии >5 KiB, чтение последнего маркера и показ PNG проходят full/compact; отсутствие capability явно видно UI; UI не обещает то, чего выбранный профиль не умеет. Не заставлять модель обходить вложения через shell.

### P1 — интеграция paste/vision только с измерениями

Сначала закончить review отдельной ветки, затем интегрировать в самостоятельном проходе. Ограничить очередь подготовки, отменять ненужные работы, привязать результат к исходному draft/session, кешировать подготовленные изображения по artifact+параметрам, не декодировать одинаковое изображение на каждом раунде. Capability хранить для endpoint/model; каталог ID сам по себе не доказывает vision.

Приёмка: 30 повторов на 1080p/4K/8K, фото/шум/alpha, текст 5 KiB/1 MiB/8 MiB; pending first-paint p95 <100 мс после получения native snapshot, UI stall <50 мс, отдельные latency кодирования/записи, peak heap/RSS; переключение чата и отмена во время подготовки не переносят вложение. Ограничения размера и памяти проверяются до тяжёлой аллокации. Пять раундов с одной картинкой переиспользуют подготовленные байты. Отдельный live vision fixture с известным ответом и малым бюджетом.

### P2 — повторный rewind

`turnChangeIds` продолжает возвращать уже отменённые change IDs: успешный undo добавляет activity без удаления/маркировки исходных IDs. Повторный клик получает UNKNOWN_CHANGE. Сохранять durable undone-ID и показывать только оставшиеся изменения. Приёмка: повторный rewind пуст, restart сохраняет состояние; внешняя правка не перезаписывается, частичный откат нескольких файлов объясняется отдельно. Файлы, созданные процессом, не выдавать за покрытые журналом точных правок.

### P2 — сравнение моделей: потеря частичных результатов

При остановке текущая сторона хранит завершённые попытки только в UI; итоговый record собирается из целиком завершённых suite. Сохранять каждую попытку инкрементально с расходом и состоянием interrupted. ID с точностью до секунды заменить на уникальный suffix/exclusive-create. Приёмка: остановка после первого результата и restart сохраняют его; два быстрых старта не перезаписывают историю; ошибки и порядок repeats сохраняются.

### P2 — бюджеты как часть продукта

Использованный здесь денежный guard — временный инструмент аудита, не функция Chiller. Добавить единый ledger на run+helpers+provider-retries, резерв максимального следующего ответа и входа, учёт неизвестного исхода, пользовательский stop-limit. Приёмка: параллельные helpers и retry не обходят потолок; рестарт не обнуляет потраченный резерв; usage и оценки различаются в UI.

### P2 — расширить жизненные сценарии, не только unit helpers

Тестировать auto-verify при смене сессии/настроек/permissions, повторный rewind и частичный undo, comparison cancel/restart, вставку при смене чата, bounded oversized image и native окно. Текущий live корпус небольшой и в основном Python: добавить Kotlin/Gradle, TypeScript, большой репозиторий, ambiguous edits, отказ web, большой результат, лимиты/429/обрыв SSE. Внешние отказы моделировать offline; live повторять 3–5 раз только с отдельным бюджетом.

## Идеи сильных функций

1. **Подтверждённый результат задачи.** Общая карточка: diff, фактически выполненные проверки, созданные artifacts и оставшиеся проблемы; done не выводится из одного текста модели. Реальный запрос «сделай график» завершается доступным графиком.
2. **Адаптивный контекст для маленькой модели.** Компактный catalog с обязательными capabilities, bounded project map, повторное использование прочитанного контекста и краткое объяснение почему модель перечитывает файл. Оценивать по успеху/раундам/входным токенам, а не размеру prompt отдельно.
3. **Безопасная точка возврата.** Обзор изменений turn с понятным покрытием undo, отличием process-effects от отслеживаемых file edits и сохранением внешних правок. Это развитие существующего rewind, не обещание полного sandbox.
4. **Мгновенная работа с материалами.** Pending-chip сразу, фоновые преобразования, большой текст как файл, полноразмерный просмотр и явное «модель видит картинку / только имя». Это сильнее ещё десятка мелких tools.

## Границы готовности

Рекомендовано: Full + DeepSeek для небольших и средних задач под review, проверка diff и тестов перед принятием. Большой текст и выдача файлов подтверждены live. Web и read-only помощники работают в проверенных сценариях.

Не подтверждено: Gemma/vLLM, live vision, thinking-enabled в этой ночи, native clipboard first-paint, полноценная нативная UI-приёмка, длительный soak, актуальная Windows-сборка. Cwd/path guards процессов не являются OS sandbox. Автономность на чужом/недоверенном проекте без наблюдения пока не обещать.
