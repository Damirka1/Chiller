# Chiller — план гармонизации интерфейса

Дата: 17 октября 2026. Статус: основной визуальный проход реализован; Keychain, проверка API в UI и полная матрица доступности остаются отдельными задачами.
Основание: предоставленные пользователем скриншоты Codex и текущего Chiller.
Focus — основной сценарий; Studio остаётся вариантом той же рабочей области.

## Диагноз

Проблема текущего экрана в композиции и иерархии, а не в необходимости менять Compose.
Приветствие и composer образуют крупный блок в центре, оставляя низ без назначения.
При первом сообщении поле перемещается вниз и меняет ширину с 640 до 740 dp.
Sidebar имеет чрезмерные разрывы между короткими разделами; название продукта,
breadcrumb и приветствие повторяют контекст. Focus/Studio заметнее многих рабочих действий.
Маленький бледный footer плохо читается, а зелёная точка ошибочно обещает проверенное соединение.
Скриншоты имеют разные пропорции: сравнивать будущие варианты нужно при одинаковом размере окна.

## 1. Сначала утвердить композицию Focus

- Единый внешний фон окна, спокойная боковая панель и белая рабочая поверхность.
- Sidebar: 240–260 dp, внутренние поля 12–16 dp, строки 32–36 dp. Отступ между разделами 20–24 dp.
- Вверху название Chiller и одно действие нового диалога; убрать дублирующий значок создания.
- Проект и его диалоги составляют понятную группу. Названия обрезаются в одну строку,
  полный текст доступен по наведению и средствам доступности.
- Не добавлять узкую дополнительную панель иконок, пока нет отдельных разделов для неё.
- Header высотой 44–48 dp: текущий проект/чат и вторичные действия. Переключатель
  Focus/Studio — компактное управление видом с понятной подсказкой.
- Приветствие: небольшой нейтральный знак и строка «Что сделаем в Chiller?» после
  выбора проекта; до выбора — ясное действие «Открыть проект». Заголовок 24–28 sp.
- Composer закреплён снизу и до, и после первого сообщения; ширина 720–800 dp,
  нижний отступ 20–24 dp. Общая ось с сообщениями. Начальная высота 100–120 dp,
  рост по содержимому до 220 dp, далее внутренний скролл.
- Над composer компактная строка текущего проекта; внутри снизу режим слева,
  модель и отправка справа. Не показывать неработающие вложения/worktree/голосовые функции.
- Две необязательные подсказки задач рядом с приветствием, а не ещё одна панель под вводом.
- Убрать постоянную нижнюю техническую полоску: состояние модели относится к её селектору,
  оценка контекста открывается по запросу. Ошибки остаются видимыми и доступными.

## 2. Зафиксировать визуальные правила

- Типографика: основной текст 14 sp/21 sp, навигация 13 sp/18 sp, подписи 12 sp/16 sp.
  Использовать одну платформенную sans-serif гарнитуру и отдельный моноширинный шрифт для кода.
- Шкала расстояний 4/8/12/16/24/32 dp; избегать случайных промежуточных значений.
- Светлая тема: нейтральный белый canvas, слегка серый sidebar; тёмная — собственные
  уровни поверхностей, а не инверсия. Проверить читаемость вторичного текста.
- Скругления: небольшие у кнопок, 14–18 dp у composer, 10–12 dp у панелей.
- Тонкая рамка composer и слабая тень для отделения от фона. Стекло не требуется.
- Иконки одной толщины 16–18 dp, стабильные области нажатия от 28–32 dp.
- Зелёный — ограниченно для бренда и подтверждённого результата. Hover, selected,
  pressed, disabled и keyboard focus должны различаться в обеих темах.

## 3. Довести рабочий диалог и Studio

- Сообщения и composer имеют общую ширину. Ответы не заключать в лишние карточки.
- Инструменты сгруппировать в компактные строки: действие, файл, фактический статус;
  вывод и diff раскрываются. Ошибки и вопросы не прячутся внутри свёрнутых групп.
- Код и diff: читаемый моноширинный текст, копирование, горизонтальный скролл,
  номера строк и знаки изменений. Длинный вывод открывается отдельно.
- Studio использует ту же основу; справа панель изменений 320–380 dp с resize.
  На узком окне — переключаемая панель, без сжатия диалога до нечитаемого состояния.
- Смена режима сохраняет draft, выбранный чат, положение чтения и текущую задачу.
- Анимации 120–180 ms для состояний и 180–220 ms для панелей, без постоянной пульсации.
  Reduced motion убирает пространственные переходы. Composer не прыгает при отправке.

## 4. Сделать настройки и подключение однозначными

Фактическое поведение сейчас: URL/model/workspace записываются в settings.json;
введённый ключ остаётся только в памяти DesktopController до закрытия приложения.
apiKeyConfigured проверяет наличие строки, а не авторизацию у провайдера.
Ключ пользователя не читался, запросы к DeepSeek в рамках этого планирования не выполнялись.

- Разделить состояния: «Ключ не задан», «Ключ задан · не проверен», «Проверка…»,
  «Проверено» с датой/моделью и конкретная ошибка. Смена профиля сбрасывает проверку.
- Разделить действия «Применить настройки» и «Проверить подключение».
- Для постоянного хранения добавить macOS Keychain; явно выбирать хранение до выхода
  или в системном хранилище. Не писать ключ в обычный JSON. Другие ОС — отдельные адаптеры.
- Проверка соединения — отдельное явно запущенное действие с ограниченным бюджетом;
  отсутствие сетевой ошибки при сохранении не считается проверкой API.
- Настройки визуально разделить на «Подключение», «Внешний вид» и «Разрешения».
  Кнопка отмены не должна уже применять изменения переключателей.

## Порядок реализации и приёмка

1. Подготовить сравнимые макеты Focus: пустой экран и разговор в окне 1280×860,
   светлая/тёмная темы. Согласовать геометрию до переписывания компонентов.
2. Обновить токены и базовые контролы; реализовать sidebar/header/composer.
3. Довести conversation, tool groups и Studio на тех же компонентах.
4. Реализовать честные состояния подключения и хранение ключа; проверить настройки.
5. Проверить реальную desktop-сборку: пустой экран, длинный чат, выполнение,
   ошибка, вопрос, diff, обе темы, узкое окно и увеличение текста.

Критерии: без скачка поля при первом сообщении; одинаковая сетка сообщений и ввода;
нет обрезанных действий на 960×720; читаемые подписи; видимый focus; рабочие Tab,
Cmd/Ctrl+Enter, Cmd/Ctrl+N и Escape; сохранение draft при ошибках и смене layout.
Подтверждение API допускается только после фактического ответа. Сохранение ключа
в Keychain проверяется перезапуском без вывода секрета в логи.

Основные файлы реализации: design-system/ChillerTheme.kt и ChillerControls.kt;
app-desktop/ui/ChillerApp.kt; app-desktop/di/DesktopController.kt и composition root Main.kt.
Изменения дизайна не требуют переписывать файловое/агентное ядро или менять UI-стек.
