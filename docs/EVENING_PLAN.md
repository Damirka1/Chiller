## 2. Дизайн: рекомендуемый вариант

Сохранить нейтральный стиль и общую композицию. Главная проблема — избыточная высота ввода и распавшаяся строка управления. Решение: компактный двухстрочный composer, который растёт только вместе с текстом.

```text
╭────────────────────────────────────────────────────╮
│ Напишите задачу…                                   │
│                                                    │
│ План ⌄   DeepSeek Flash ⌄                       ↑  │
╰────────────────────────────────────────────────────╯
```

Схема показывает группировку, а не обязательную пустую строку: свободное место не резервируется. Поле текста и toolbar имеют небольшой фиксированный промежуток.

### D1. Геометрия и ввод — первый приоритет

Файлы: app-desktop/.../ui/ChillerApp.kt, при необходимости design-system/.../ChillerControls.kt. Общие контракты не менять.

1. Найти Composer и убрать суммирование большого минимального text-area, вертикальных padding и spacer. Начальная высота всего блока при fontScale=1: **80–88 dp**, текстовая область около 24–28 dp. Внешняя ширина до 760 dp, отступ от низа 16–20 dp.
2. Автоматический рост по строкам до общей высоты около 200 dp; затем внутренний scroll. Длинная вставка не должна закрывать всю историю. При очистке возвращать компактную высоту.
3. Внутренние отступы 10–12 dp; радиус 14–16 dp; основной текст 14 sp, toolbar 12–13 sp. Цвета брать из темы, без новых случайных оттенков.
4. Пустая отправка disabled; при выполнении на том же месте Stop. Сохранить SendReceipt, pending guard, IME composition и очистку только принятого снимка текста. Не переписывать эту логику ради layout.

Приёмка: пустой ввод, 1/3/10 строк, большая вставка, отказ отправки, быстрые повторные клики, streaming/Stop; черновик не исчезает после ошибки или смены режима.

### D2. План и выбор модели — второй приоритет

1. Слева в общей toolbar поставить **два соседних компактных контрола**: «План ⌄» и «DeepSeek Flash ⌄», промежуток 8 dp. Справа оставить отправку, между группами — один гибкий spacer.
2. Ширина модели определяется содержимым и доступным местом. Убрать внутренний weight, растягивающий кнопку и отрывающий chevron. Стрелка всегда рядом с подписью, gap 4–6 dp. Длинный model ID сокращать с tooltip полного ID.
3. Одинаковые высота, baseline, hover, focus и стиль меню у обоих контролов. В списке режима показать короткое объяснение реальных ограничений; выбранный пункт отметить. Не добавлять неподдерживаемые режимы.
4. В узком окне сначала сокращать модель, затем переносить toolbar целиком на дополнительную строку. Не уменьшать шрифт ради размещения. При fontScale=2 допустить рост высоты; размеры 80–88 dp относятся только к обычному масштабу.

Приёмка: длинное имя модели, раскрытие и Escape, клавиатурная навигация, running state, смена модели с сохранением черновика; chevron не стоит отдельно у правой границы.

### D3. Контекст проекта и гармония экрана

1. Убрать отдельную строку «Выбрать проект» над composer в пустом состоянии: открытие уже доступно в sidebar и welcome. При выбранном проекте показывать компактную контекстную подпись/чип, только если она помогает понять цель запроса.
2. Не добавлять постоянно видимые статусы API под вводом. Ошибку размещать рядом с действием, подробности — по раскрытию; ключ задан не означает подключение проверено.
3. Сохранить одну ширину оси сообщений и composer, спокойный welcome и сдержанный бренд. Не вводить новые карточки, стекло или декоративные панели.
4. Проверить sidebar, Studio toolbar и settings на обрезание при увеличении шрифта. Не решать проблему только раздуванием sidebar: при нехватке места переносить/скрывать второстепенные подписи с доступной альтернативой.
5. Анимации только для focus/hover, раскрытия и переходов 100–180 ms; reduced motion отключает их. Положение ввода при росте текста должно быть предсказуемым.

### D4. Приёмка дизайна

Собрать отдельный offline preview, не закрывая пользовательский Chiller. Светлая/тёмная темы; Focus/Studio; окна примерно 1280×860 и 960×720; fontScale 1/1.5/2. Синтетические empty, streaming, tool error, long history. Проверить drag Studio и доступные кнопки ширины отдельно. Сохранить реальные снимки и перечислить непроверенные сценарии. IME и VoiceOver не объявлять проверенными по unit tests.

## 3. Дополнение пользователя: каталог моделей и субагенты

### M1. Каталог моделей указанного API

Приоритет сразу после compact composer; providers/** — worker, contracts и controller integration — координатор.

- Ввести отдельный bounded GET models discovery для выбранного endpoint. Если base URL уже заканчивается /v1, добавлять /models; не получать /v1/v1/models. Сохранять пользовательский prefix gateway. Для нестандартного API предусмотреть явный models URL в профиле, без угадывания нескольких адресов подряд.
- Использовать credential только текущего профиля/origin, запретить пересылку авторизации при redirect на другой origin. Timeout, отмена, ограничение размера ответа и числа моделей, sanitized errors, отсутствие логирования ключа.
- Разбирать стандартный data[].id, сохранять точные уникальные ID. Не выводить версию из выдуманного friendly label: версии 4.0/4.1 различаются только если API возвращает разные ID/метаданные. Alias вроде deepseek-flash сам по себе не доказывает конкретную версию. Не утверждать существование конкретных versioned IDs до ответа API.
- В настройках кнопка «Обновить модели», loading/error/empty/unsupported, время последнего успешного обновления. Кэш отдельно на endpoint/profile; отменённый или запоздалый ответ прежнего профиля не заменяет текущий список. Не дергать сеть на каждом раскрытии меню.
- В picker объединять discovered IDs и явно настроенные ручные ID с различимой пометкой. При 404/405/недоступности discovery сохранять ручной ввод и выбранную модель. Не удалять историческое авторство при исчезновении модели из каталога.
- Каталог не доказывает поддержку tools, reasoning, context length или успешность generation: capabilities остаются отдельными. Discovery не вызывает chat/completions.
- Fixture tests: base URL с/без /v1 и gateway prefix; два разных versioned ID; alias; duplicates/unknown fields; empty/malformed/oversized; 401/404/429/timeout/cancel; смена профиля в полёте; сохранение ручной модели. Live discovery не нужен для проверки реализации; реальный запрос отдельно записывать как read-only discovery, не как проверку генерации.

### A1. Субагенты внутри Chiller

Это продуктовая возможность Chiller, отдельная от работников Codex, реализующих проект. Пользователь поднял её из отложенного V1 в текущий план. В 15:00–15:30 спроектировать полный контракт; после 15:30 реализовать минимальный сквозной вариант с offline fixtures, не декоративные кнопки.

Предлагаемый набор инструментов, окончательные имена фиксирует координатор после аудита:

| Инструмент | Назначение |
|---|---|
| spawn_agent | Создать дочернюю задачу: цель, контекст, выбранный model ID, область файлов, лимиты |
| list_agents | Ограниченный снимок состояний дочерних задач |
| send_agent_message | Доставить сообщение с ID, дедупликацией и порядком; отличать steering от нового запуска |
| wait_agents | Ожидание изменения/завершения с cursor и bounded timeout; без busy polling |
| cancel_agent | Отмена дочерней задачи и её процессов, финальный статус |
| get_agent_result | Краткий структурированный результат и ссылки на артефакты; bounded output |

- Контракт: parentRunId/agentId/taskId, queued/running/waiting/completed/failed/cancelled/interrupted; последовательность событий, mailbox, модель, usage, результат, изменённые пути, выполненные проверки и ограничения.
- Первый вариант: глубина 1, максимум 3 дочерних агента, общий лимит параллелизма и бюджета родителя плюс отдельные меньшие лимиты детей. Исчерпание общего бюджета останавливает запуск новых задач. Отмена родителя каскадная; restart не перезапускает неизвестные побочные эффекты.
- Дочерний агент наследует системную политику, workspace и не более широкие разрешения. Plan остаётся read-only у всех потомков. Секреты не включать в task context/mailbox/journal. Контекст передавать ограниченной выборкой с происхождением, не копировать безграничную историю.
- Сначала read-only делегация (анализ/поиск/ревью) и полный lifecycle. Для write agents до включения обязательны файловые ownership leases, сериализация конфликтующих effects и snapshot validation; shared checkout не является изоляцией. Не выдавать unrestricted write workers до готовности этого слоя. Worktrees — последующее расширение.
- Сообщения и ответы детей — данные, а не новые пользовательские разрешения. Только родитель решает об интеграции результата. Дочерние инструкции не расширяют доступ и не разрешают внешние действия.
- UI: компактная группа «Субагенты · N», имя задачи/модель/статус/расход, раскрываемый результат и Stop. События не заливают основной transcript. Показывать реально работающий run, не синтетическое «готово».
- Порядок реализации: shared contracts coordinator → supervisor + event journal → tools adapters → controller/UI → offline integration. Workers редактируют только согласованные непересекающиеся пути; одного большого одновременного рефакторинга AgentCoordinator избегать.
- Приёмка: parent запускает два synthetic children; обмен сообщениями; ожидание с cursor; сбор результатов; отмена и budget exhaustion; duplicate message; late result после cancel; restart interrupted без replay; запрет повышения permissions; конфликт путей до включения writes. Платная проверка нескольких реальных моделей не входит в текущее разрешение.

## 6. Правила для экономичной модели

Координатор читает AGENTS.md, этот план, RUN_REPORT, README, MODULES, CONTRACTS и DESIGN; contracts/Contracts.kt важнее старых API sketches. По умолчанию один gpt-6-luna worker для D1–D3, только app-desktop/.../ui/** и при согласовании design-system/**. Второй gpt-6-luna worker — M1/providers; третий — A1 после фиксации координатором контрактов и границ. До трёх workers только для независимых конкретных задач с назначенными путями; не тратить их на повторные обзоры. Без рекурсивной делегации. Состав и владельцы фиксируются до редактирования; coordinator владеет Main/di/contracts/build и Git.

Работать малыми завершёнными шагами. Не запускать несколько Gradle сборок одновременно. Тестировать поведение, а не копию layout-констант; низкорисковую геометрию проверять реальным preview. В конце интеграции выполнить `./gradlew check :evals:offlineSmoke :app-desktop:createDistributable`. Отдельно отметить последующие изменения, если они не вошли в проверенную сборку.

Не искать ключи, не выводить .env, не выполнять новые live API calls: прежнее одноразовое разрешение использовано. Сетевые ответы проверять synthetic/loopback fixtures. Не закрывать пользовательский процесс с memory-only ключом. Не push/publish. RUN_REPORT обновлять после значимых checkpoint; пользователю писать только при готовности, серьёзном сбое или необходимом действии. Ограничения аккаунта расписание не отменяет.
