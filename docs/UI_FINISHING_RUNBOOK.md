# Chiller — подробный план завершения интерфейса

Дата: 17 октября 2026. База: 75338aa, ветка master.
Статус: план; задачи ниже ещё не выполнены. В этом проходе меняется только документация.
Документ предназначен для последовательной реализации небольшой моделью.

## 1. Результат и границы

Сохранить принятую композицию Focus: sidebar 248 dp, спокойное приветствие,
composer снизу, общая ось сообщений и ввода до 760 dp, светлая и тёмная темы.
Studio — тот же чат с дополнительной панелью. Не начинать третий редизайн.

Результат этой итерации:
- имя модели у ответа, сохранённое в истории и экспорте;
- понятные состояния генерации, инструментов и отправки;
- сохранность черновика и удобный выбор модели;
- более удобная история, Studio и настройки;
- обычная/компактная плотность, умеренная анимация и проверенная клавиатура.

Не включать в эту итерацию: MCP, браузер, новые файловые инструменты, LSP,
голос, загрузку изображений, полноценный Markdown-движок, миграцию UI-стека,
автоматическое возобновление неизвестной операции, новую платформенную матрицу.
Keychain — отдельная последующая задача, не условие завершения визуальной части.

## 2. Правила исполнения

1. Сначала прочитать AGENTS.md, docs/RUN_REPORT.md, этот документ и фактические
   contracts/src/main/kotlin/dev/chiller/contracts/Contracts.kt.
2. Проверить git status и ветку. Сохранять пользовательские изменения; работать в master.
3. Выполнять одну карточку или одну указанную пару связанных карточек за раз.
4. После карточки: проверить её критерии, записать результат в RUN_REPORT, сохранить локальный commit.
5. Общие contracts, composition root Main.kt и build-файлы меняет один координатор.
   Один экономный исполнитель может работать последовательно во всех этих ролях.
6. Если делегирование уже разрешено: gpt-6-luna, максимум 3 workers, без вложенной
   делегации; назначать разные файлы. ChillerApp.kt имеет только одного writer.
7. Gradle запускает только координатор, без параллельных сборок одного checkout.
8. Не печатать ключи, не читать настоящий .env в тестах. Использовать synthetic fixtures.
   Ранее одобренный ОДИН API-запрос уже выполнен; разрешение не распространяется на новые запросы.
9. Не push, не публиковать и не добавлять фоновые расписания.
10. Не заменять непроверенную функцию заглушкой с видом работающей. GUI-проверка
    на fixture проверяет представление, но не подтверждает реальное применение diff.

## 3. Что уже есть — не реализовывать второй раз

- 10 модулей Kotlin/Compose, рабочий coordinator и JSONL EventStore.
- AgentMessage хранит role/content/toolCalls/toolCallId/replay, но пока не автора модели.
- Provider вручную формирует wire JSON в ChatCompletionsProvider: локальные поля
  нельзя случайно отправлять в API при добавлении metadata.
- AgentCoordinator получает model в конструкторе, журналирует сообщения и активности.
- Activity сейчас связывается с сообщениями в UI по позиции: для новых групп этого недостаточно.
- Настройка профиля сейчас создаёт новый диалог. Не менять эту политику скрытно.
- UI уже сохраняет черновики разных сессий в памяти, но очищает текущий сразу при onSend.
- Export Markdown/JSON, копирование code block, горизонтальный scroll кода/diff уже есть.
- Настройки уже применяют переключатели только при Apply; сохранить поведение Cancel.
- Sidebar, header, conversation, settings пока находятся в ChillerApp.kt.
- Native menus уже реализованы. Cmd/Ctrl+Enter, Cmd/Ctrl+N, Escape под CUA не подтверждены.
- Панель Studio имеет draggable divider 280–480 dp; её фактический resize ещё не принят.
- .env/API_TOKEN поддержан; UI ключ — память процесса, без Keychain.
- Последняя общая проверка: 51 тест, offlineSmoke, macOS package. Число тестов —
  справочная база, не целевой KPI и не основание пропускать проверку новых изменений.

## M1. Сохраняемый автор ответа

**Файлы:** Contracts.kt, AgentCoordinator.kt, DesktopController.kt, тесты contracts/core.
**Владелец:** координатор. Зависимостей нет.

Предлагаемый контракт (внедрять в существующий файл, без дублирующих типов):
- @Serializable enum MessageOriginKind { MODEL, APPLICATION, OFFLINE }
- @Serializable data class MessageOrigin(kind: MessageOriginKind, modelId: String? = null)
- В конец AgentMessage добавить origin: MessageOrigin? = null.
- Для потокового ответа добавить в RunState activeModelId: String? = null.
Это предлагаемые изменения, а не уже существующие API. Сначала реализовать и
скомпилировать их одним исполнителем; затем выдавать зависимые задачи.

Шаги:
1. Значения по умолчанию обеспечивают чтение старых JSONL без миграции файлов.
2. В начале run зафиксировать модель запроса. У новых assistant-ответов выставлять
   origin=MODEL/modelId из снимка запуска ДО appendMessage/журналирования.
3. До подтверждённого ответа provider использовать идентификатор запрошенной модели;
   не приписывать ей неизвестную версию/реальный backend. modelId хранить полностью.
4. У offline-ответа DesktopController явно ставить OFFLINE, у новых уведомлений
   приложения — APPLICATION. Пользовательские и tool-сообщения не переименовывать.
5. Не класть origin в replay: replay предназначен для обязательных данных протокола.
6. Не переписывать старую историю на основании нынешних настроек.
7. Проверить wire mapper: origin/activeModelId не должны попасть в messages API.
8. При restore сохранить origin; при завершении/ошибке потоковый статус не должен
   продолжать показывать модель прошлой задачи как текущую генерацию.

Приёмка/тесты:
- Старый JSON AgentMessage без origin читается.
- Ответ модели A сохраняется, восстанавливается после restart и остаётся A,
  даже когда новый coordinator создан с моделью B.
- Offline-ответ не выглядит как ответ DeepSeek.
- Provider fixture подтверждает отсутствие локальной metadata в запросе и
  сохранение прежнего reasoning replay.

## M2. Подпись и копирование ответа, экспорт

**Файлы:** UI/MessagePresentation.kt (новый), ChillerApp.kt, SessionExport.kt и его тесты.
**Зависимость:** M1.

Правила подписи в одном helper, без сетевых вызовов:
| Источник | Подпись |
|---|---|
| user | Вы |
| MODEL + deepseek-flash | DeepSeek Flash |
| MODEL + другой ID | Читаемое имя/ID с визуальным ellipsis; полный ID в tooltip |
| OFFLINE | Chiller · offline |
| APPLICATION | Chiller |
| Старый assistant без origin | Ассистент |

Шаги:
1. Message composable получает полное AgentMessage или вычисленную подпись,
   а не только role/content. Не читать текущий providerModel для старых сообщений.
2. Streaming использует activeModelId текущего run. Одинаковый header до и после завершения.
3. Имя 12–13 sp, medium; тело 14 sp/22–23 sp. Одна нейтральная иконка ассистента,
   без набора логотипов провайдеров. Цвет бренда не должен конкурировать с diff.
4. Добавить «Копировать ответ»: копирует исходный текст целиком, без имени/даты/UI.
   Кнопка доступна с клавиатуры, подтверждение «Скопировано» краткое.
5. Markdown export добавляет имя модели к assistant-разделу; JSON сохраняет origin.
   Старые exports и redaction/replay исключения не ломать.

Приёмка: диалог с A, B, offline и старым ответом имеет четыре корректные подписи;
переключение модели не меняет историю; экспорт отражает автора без приватного replay.
Тестировать таблицу преобразований и round-trip экспорта, не pixel positions.

## T1. Надёжная связь инструментов с ответом

**Файлы:** Contracts.kt, AgentCoordinator.kt, ConversationProjection.kt (новый), tests.
**Зависимость:** M1. Shared type changes только у координатора.

Шаги:
1. Добавить Activity.toolCallId: String? = null в конец существующего типа.
2. При создании новой Activity записывать id конкретного ToolCall; сохранять поле
   во всех running/completed/failed copies и событиях журнала.
3. Проекция UI связывает activity с assistant.toolCalls по ID, а не drop/take(offset).
4. Группировать только последовательные действия одного assistant tool-round;
   не объединять через сообщение пользователя, вопрос, ошибку или следующий round.
5. Старые Activity без связи показывать отдельным списком «Действия сессии»;
   не угадывать принадлежность и не прятать их из истории.
6. Undo продолжает использовать реальный change ID из результата, не toolCallId.

Приёмка: два round с read/edit, затем отмена/ошибка и restart не переставляют
активности между ответами. Старый журнал виден без потери действий. Никакие
файловые операции не исполняются из UI-проекции.

## T2. Группы инструментов и состояние работы

**Файлы:** UI projection/composables. Зависимость T1.

Шаги:
1. Одна операция — текущая компактная строка. Несколько — общий сворачиваемый header.
2. Header строить по фактическим результатам: «Прочитано 3 файла», «Изменены 2 файла».
   Считать уникальные пути успешных операций; для смешанного набора — «4 действия».
   Если путь неизвестен, не заявлять количество файлов.
3. Running: показать конкретное действие; failed/conflict всегда видимы,
   даже если остальная группа свёрнута. Вопрос пользователя — отдельная открытая карточка.
4. Индикатор над ответом: preparing → «Подготовка…», streaming →
   «<модель> отвечает…», executing → подпись текущего инструмента,
   completed → убрать индикатор, cancelled/failed → показать действительный исход.
5. Не выводить «Проверено» только потому, что текст ответа содержит слово «тесты».
6. Раскрытие 160–200 ms; reduced motion — без пространственного перехода.
   Не сбрасывать scroll и раскрытие соседних элементов при очередном delta.

Приёмка: synthetic states idle/streaming/running/failed/cancelled/question в обеих
темах; отсутствует вечный spinner после остановки; ошибка не спрятана в группе.

## C1. Подтверждение отправки и сохранность черновика

**Файлы:** DesktopController.kt, Main.kt, composer/draft state, core при необходимости.
**Зависимость:** M2. Не переписывать весь state management.

Проблема: сейчас UI вызывает onSend и сразу обнуляет draft, даже если контроллер
не начал задачу (нет workspace, ошибка настройки, занятость).

Шаги:
1. В desktop-слое ввести тип SendReceipt с accepted/rejected, sessionId,
   clientRequestId и безопасной причиной отказа. Это не provider DTO.
2. UI создаёт request ID и снимок текста, помечает отправку pending, блокирует
   повтор того же запроса. Контроллер принимает под существующим commands Mutex.
3. Accepted возвращать только после регистрации user-message/запуска: использовать
   явный сигнал из coordinator после durable append, не таймер и не догадку по status.
   Offline-путь подтверждает после успешного append своих сообщений.
4. До accepted черновик сохраняется. После accepted очищать только если текст и
   sessionId всё ещё совпадают с отправленным снимком; новый ввод пользователя не стирать.
5. Rejected оставляет текст и понятную ошибку. После принятия и последующей ошибки
   сети сообщение остаётся в истории; предложить «Вернуть текст в поле», без auto-resend.
6. Stop отменяет run; после него нет неявного повторного запроса и side effects.
7. Отделять pending отправки от streaming; Send/Stop не мерцают и не меняют размер composer.

Тесты: отказ без workspace сохраняет draft; двукратный клик даёт один accepted;
задержанный ack для прежней сессии не очищает новый draft; сбой до и после append
не создаёт дублирующего user-message при восстановлении. Не тестировать платным API.

## C2. Компактный выбор модели

**Файлы:** DesktopSettings/Controller, composer popup, Main.kt. Зависимость C1/M2.

Шаги:
1. Нажатие на модель открывает popup: текущая модель, вручную сохранённые модели
   этого endpoint, пункт «Настройки моделей». Не открывать сразу большой dialog.
2. Хранить небольшой список последних model IDs по нормализованному endpoint в settings;
   список начинается с текущего реального значения. Не заявлять серверные capabilities.
3. Разрешить ручной ввод ID через настройки, с trim/проверкой непустоты.
4. Выбор другой модели создаёт новый чат, как нынешнее configure; пояснить это
   в popup. Draft перенести явно в новый чат только как пользовательский черновик.
   История текущего чата и origin старых ответов неизменны.
5. Во время run выбор заблокирован; popup закрывается Escape, фокус возвращается
   к кнопке, выбранный пункт обозначен и цветом, и checkmark.
6. Не переносить credential на другой host автоматически при смене endpoint.
   Источник ключа и область его применения должны быть определены явно.

Приёмка: модели A/B на synthetic provider; смена во время run невозможна;
изменение endpoint сбрасывает проверку соединения; длинные ID не ломают composer.

## H1. История диалогов

**Файлы:** LocalStores.kt, DesktopController.kt, sidebar, SessionExport при необходимости.
**Зависимость:** M2.

Шаги:
1. Переименование реализовать событием session.renamed {title}, а не переписыванием
   user-message. trim, 1–120 символов, отмена ничего не пишет.
2. EventStore.list использует последнее корректное rename; иначе прежний first-user fallback.
   Обновить список и header сразу после сохранения; restart сохраняет название.
3. Показать группы «Сегодня», «Вчера», «Ранее» по локальному времени пользователя;
   парсить timestamp как Instant. Не сортировать по локализованным строкам.
4. Tooltip полного заголовка и меню строки: «Переименовать», «Экспорт Markdown»,
   «Экспорт JSON». Не добавлять неработающее удаление/архивирование.
5. Экспорт из меню должен явно использовать ID выбранной строки, а не текущего чата.
6. Единая высота строк 32–36 dp, selected и hover различимы, активная строка не прыгает.

Тесты: rename/restart, старый журнал, пустой/длинный заголовок, экспорт неактивной
сессии. Группировку времени тестировать с внедряемыми Clock/ZoneId на границе суток.

## P1. Настройки и честная проверка подключения

**Файлы:** DesktopController/Settings, providers при необходимости, UI settings.
**Зависимости:** C2/S1. Не превращать passive probe в скрытый платный запрос.

Шаги:
1. Разделы «Модели», «Внешний вид», «Разрешения»; одна транзакция Apply/Cancel.
   В разделе модели: endpoint, ID, thinking, источник ключа, состояние проверки.
2. Состояния: MissingKey, ConfiguredUnverified, Checking, Verified, Failed.
   Verified содержит время и снимок endpoint/model/options + revision ключа
   (локальный счётчик, без хранения/логирования самого секрета или его отпечатка).
3. Смена ключа/endpoint/model/options сбрасывает Verified. Поздний ответ проверки
   старого профиля не должен пометить новый как проверенный.
